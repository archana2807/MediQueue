1. PROJECT OVERVIEW QUESTIONS
================================================================================

Q1: What is MediQueue and what problem does it solve?
A: MediQueue is an AI-Powered Hospital Management System that streamlines
   hospital operations for three user roles: Admin, Doctor, and Patient.
   It solves problems like manual appointment scheduling, inefficient queue
   management, lack of quick medical report analysis, and poor patient
   experience by integrating AI-powered features such as a conversational
   chatbot, symptom-based doctor recommendation, and auto-generated clinical
   summaries.

Q2: What are the main features of MediQueue?
A: The main features include:
   - Role-based authentication (Admin, Doctor, Patient)
   - Dashboard with real-time statistics
   - Appointment management (CRUD with conflict detection)
   - Doctor management (Admin-only)
   - Real-time queue management
   - AI Chatbot with multi-intent detection (FAQ, Doctor Search, Symptom
     Triage, Appointment Booking)
   - AI Medical Report Analyzer (PDF upload or text paste)
   - AI-Powered Doctor Notes Summary
   - Patient Medical History timeline

Q3: Who are the target users of this system?
A: The target users are:
   - Admins: Hospital administrators who manage doctors, appointments,
     and oversee queue operations.
   - Doctors: Medical professionals who manage patient queues, write
     consultation notes, and generate AI summaries.
   - Patients: Individuals who register, book appointments (manually or
     via AI chatbot), and access their medical history and reports.

Q4: What makes MediQueue different from traditional hospital management
    systems?
A: MediQueue differentiates itself through deep AI integration:
   - Conversational appointment booking via natural language chatbot
   - RAG-based FAQ system using pgvector for accurate context-aware answers
   - Symptom-to-specialization triage using LLM mapping
   - AI-powered medical report analysis with structured markdown output
   - Auto-generated clinical summaries from doctor notes
   - All AI features are integrated into the existing workflow, not
     standalone tools.

2. TECHNICAL STACK & ARCHITECTURE QUESTIONS
================================================================================

Q5: What is the tech stack used in MediQueue?
A: The tech stack is:
   - Frontend: Next.js 16 (App Router), React 19, TypeScript 5
   - Styling: Tailwind CSS 4, shadcn/ui (Radix UI primitives)
   - Forms: React Hook Form v7 + Zod v4 validation
   - State/Tables: TanStack React Table v8
   - Authentication: NextAuth.js v4 (JWT strategy)
   - Database: PostgreSQL (Neon serverless) + pgvector extension
   - AI/LLM: OpenRouter (GPT model), OpenAI embeddings via LangChain
   - PDF Parsing: pdf2json, pdf-parse
   - Testing: Jest 30 + Testing Library
   - Deployment: Vercel

Q6: Why was Next.js App Router chosen over Pages Router?
A: The App Router was chosen for:
   - React Server Components (RSC): Dashboard pages fetch data on the
     server, reducing client-side JavaScript and improving initial load.
   - Route Groups: Separate layouts for auth pages (no sidebar) and
     dashboard pages (with sidebar) using (auth) and (dashboard) groups.
   - Colocation: API routes, pages, and layouts coexist in the same
     directory structure.
   - Built-in streaming and loading states.
   - Better TypeScript support and file-system based routing.

Q7: Why is PostgreSQL used instead of MongoDB or other databases?
A: PostgreSQL was chosen because:
   - Relational data model fits the domain (users, doctors, appointments
     have clear relationships and foreign keys).
   - pgvector extension enables vector similarity search for RAG without
     a separate vector database.
   - ACID compliance ensures transaction safety for appointment creation
     and queue management.
   - Strong data integrity with foreign key constraints.
   - Neon provides serverless PostgreSQL with auto-scaling.

Q8: Explain the project's architecture and directory structure.
A: The project follows a clean separation of concerns:
   - src/app/: Next.js App Router with route groups (auth, dashboard)
   - src/app/api/: Server-side API routes (thin controllers)
   - src/lib/queries/: Data access layer (all DB queries centralized)
   - src/lib/: Utilities, auth config, AI clients, validations
   - src/components/: Reusable UI components (shadcn/ui + custom)
   - src/components/ui/: shadcn/ui primitives (Button, Card, Dialog, etc.)
   - src/hooks/: Custom React hooks
   - src/types/: TypeScript type definitions

   This follows the pattern: API Route -> Query Function -> Database,
   keeping API routes thin and queries reusable.

Q9: What is the role of the Data Access Layer (src/lib/queries/)?
A: The Data Access Layer centralizes all database queries into dedicated
   modules (dashboard.ts, appointments.ts, doctors.ts, queue.ts, etc.).
   This provides:
   - Separation of concerns: API routes handle HTTP, queries handle DB.
   - Reusability: Same query can be used by multiple API routes.
   - Testability: Query functions can be tested independently.
   - Maintainability: Database logic changes don't ripple across API routes.
   - Transaction management: Complex operations like appointment creation
     with queue assignment use explicit BEGIN/COMMIT/ROLLBACK.

3. AUTHENTICATION & AUTHORIZATION QUESTIONS
================================================================================

Q10: How does authentication work in MediQueue?
A: Authentication uses NextAuth.js v4 with:
   - Credentials Provider: Email + password login.
   - Password Hashing: bcryptjs with 10 salt rounds.
   - JWT Strategy: Session data stored in JWT token.
   - Custom JWT Callbacks: Inject user id, role, and phone into the
     JWT token and session.
   - Custom Sign-In Page: Redirects to /login instead of default.
   - Patient Registration: New patients register via /api/auth/register.

Q11: How is authorization (role-based access control) implemented?
A: Authorization is implemented at multiple levels:
   1. Middleware (src/proxy.ts): Uses NextAuth withAuth wrapper and
      checks token.role to gate routes:
      - /doctors -> ADMIN only
      - /queue -> ADMIN + DOCTOR
      - /appointments/new -> ADMIN + PATIENT
      - /dashboard -> All authenticated users
   2. Sidebar Navigation: app-sidebar.tsx dynamically filters menu
      items based on the user's role.
   3. API Routes: Some endpoints check the session role before
      processing (e.g., doctor management).

Q12: What is stored in the JWT token and why?
A: The JWT token stores:
   - id: User's UUID (to identify the user in API calls)
   - role: User's role (ADMIN, DOCTOR, PATIENT) for route protection
   - phone: User's phone number (for patient lookup in appointment forms)
   - Standard NextAuth fields (name, email, image)
   These are injected via custom JWT and session callbacks in auth.ts,
   allowing client and server to access user context without additional
   database lookups.

Q13: How does the middleware protect routes?
A: The middleware (src/proxy.ts) uses NextAuth's withAuth wrapper:
   - It receives the JWT token on every request.
   - It checks token.role against allowed roles for each route.
   - If the role doesn't match, it redirects to /unauthorized.
   - If there's no token, it redirects to /login.
   This provides server-side route protection before the page even loads.

4. DATABASE DESIGN QUESTIONS
================================================================================

Q14: What are the main database tables in MediQueue?
A: The main tables are:
   - users: id (UUID), name, email, password, role, phone, created_at
   - doctors: id (UUID), user_id (FK->users), specialization
   - appointments: id (UUID), patient_id (FK->users), doctor_id
     (FK->doctors), appointment_date, queue_number, status, created_at
   - appointment_notes: id, appointment_id (FK->appointments),
     doctor_notes, ai_summary
   - patient_reports: id, patient_id (FK->users), report_name,
     report_url, ai_analysis, created_at
   - knowledge_chunks: id, title, content, embedding (vector)

Q15: Why is UUID used as the primary key instead of auto-incrementing
     integers?
A: UUIDs are used because:
   - They can be generated client-side without database coordination.
   - They prevent ID enumeration attacks (sequential IDs are guessable).
   - They're globally unique, making data merging and migration easier.
   - PostgreSQL supports them natively via uuid-ossp extension.
   - They work well with distributed systems.

Q16: How does the queue_number field work in appointments?
A: Queue numbers are auto-assigned when an appointment transitions from
   PENDING to CONFIRMED. The logic:
   1. A transaction is started (BEGIN).
   2. The next available queue number is calculated by finding the
      maximum queue number for the appointment date and adding 1.
   3. The appointment status is updated to CONFIRMED with the new
      queue number.
   4. The transaction is committed (COMMIT).
   5. If any step fails, ROLLBACK is executed.
   This ensures no two appointments get the same queue number on
   the same day.

Q17: What is the purpose of the knowledge_chunks table?
A: The knowledge_chunks table stores the hospital's knowledge base for
   the RAG (Retrieval-Augmented Generation) FAQ system. Each row
   contains:
   - id: Unique identifier
   - title: Topic/category of the knowledge chunk
   - content: The actual text content
   - embedding: A vector representation (generated by OpenAI's
     text-embedding-3-small model) used for similarity search.

Q18: How does the pgvector extension enable the RAG system?
A: pgvector adds a vector data type to PostgreSQL and supports:
   - Cosine similarity search using the <-> operator
   - Indexing for fast nearest-neighbor queries
   The RAG pipeline works as follows:
   1. User asks a question.
   2. The question is converted to an embedding using OpenAI's model.
   3. A SQL query finds the top 5 most similar knowledge chunks
      using pgvector's <-> operator.
   4. The retrieved chunks are passed as context to the LLM.
   5. The LLM generates an answer constrained to that context.

5. API & BACKEND QUESTIONS
================================================================================

Q19: Describe the API route structure in MediQueue.
A: API routes are in src/app/api/ and follow RESTful conventions:
   - POST /api/auth/register: Patient registration
   - GET/POST /api/auth/[...nextauth]: NextAuth handler
   - GET/POST /api/doctors: List/create doctors (Admin-only)
   - GET/PUT/DELETE /api/doctors/[id]: Doctor CRUD
   - GET/POST /api/appointments: List/create appointments
   - GET/PUT/DELETE /api/appointments/[id]: Appointment CRUD
   - GET /api/patients: List patients
   - GET /api/patients/search?phone=: Search by phone
   - GET /api/queue: List queue
   - PUT /api/queue/[id]: Update queue status
   - POST /api/chat: AI chatbot endpoint
   - POST /api/ai/report-analysis: Medical report analysis
   - POST /api/ai/summary: Doctor notes summary
   - POST /api/reports: Save report to database

Q20: How does the appointment creation flow work?
A: The appointment creation flow:
   1. Patient/Admin submits the form with doctor, date, time, symptoms.
   2. API validates the input using Zod schemas.
   3. Checks if the doctor exists and is available.
   4. Detects conflicts with existing appointments.
   5. Analyzes doctor workload (Low/Medium/High).
   6. Creates the appointment with PENDING status.
   7. Walk-in patients auto-create a user record with generated email.
   8. Returns the created appointment.

Q21: How does the walk-in patient creation work?
A: When an appointment is created for a patient not in the system:
   1. The system checks if a patient with the provided phone exists.
   2. If not, it auto-generates an email (e.g., walk-in-{phone}@hospital.com).
   3. Creates a new user record with role PATIENT and a default password.
   4. The appointment is linked to this newly created patient.
   This allows walk-in patients to be registered without manual setup.

Q22: How are database transactions used in MediQueue?
A: Transactions are used in critical multi-step operations like
   appointment creation and queue number assignment:
   - BEGIN: Start the transaction
   - Execute multiple SQL statements
   - COMMIT: Save all changes if successful
   - ROLLBACK: Undo all changes if any step fails
   This ensures data consistency, especially when updating queue
   numbers where concurrent requests could cause conflicts.

6. AI & MACHINE LEARNING QUESTIONS
================================================================================

Q23: How does the AI chatbot (MediQueue AI Assistant) work?
A: The chatbot uses an intent-classification-then-dispatch pattern:
   1. User sends a message.
   2. An LLM call classifies the intent: FAQ, DOCTOR, SYMPTOM,
      APPOINTMENT, QUEUE, or HISTORY.
   3. The appropriate handler is invoked:
      - FAQ: RAG pipeline with pgvector similarity search
      - DOCTOR: Fetches doctors from DB, answers via LLM
      - SYMPTOM: Maps symptoms to specialization, finds doctors
      - APPOINTMENT: Extracts details via LLM, creates appointment
   4. The response is returned to the user.

Q24: Explain the RAG (Retrieval-Augmented Generation) implementation.
A: The RAG implementation:
   - Pre-processing: embed-knowledge.ts script chunks hospital
     knowledge and generates embeddings using OpenAI's
     text-embedding-3-small model via LangChain.
   - Storage: Embeddings stored in knowledge_chunks table with
     pgvector extension.
   - Query-time:
     1. User question is embedded using the same model.
     2. pgvector performs nearest-neighbor search (<-> operator).
     3. Top 5 similar chunks are retrieved.
     4. Chunks are formatted as context and sent to the LLM.
     5. LLM generates an answer constrained to the retrieved context.
   This ensures accurate, grounded answers from the hospital's
   knowledge base.

Q25: How does the symptom-based doctor recommendation work?
A: The symptom triage is a two-step process:
   1. Specialization Mapping: An LLM call maps the user's symptoms
      to a medical specialization (e.g., "chest pain and shortness
      of breath" -> "Cardiology").
   2. Doctor Lookup: A database query finds all doctors with that
      specialization.
   3. If multiple doctors are found, the LLM helps present the options.
   This allows patients to describe symptoms in natural language and
   get appropriate doctor recommendations.

Q26: How does the AI medical report analyzer work?
A: The report analyzer:
   1. Accepts input as PDF upload or text paste.
   2. For PDFs: pdf2json extracts text content from the PDF.
   3. The extracted text is sent to an LLM with a structured prompt.
   4. LLM generates a structured analysis including:
      - Key Findings
      - Abnormal Results (with warnings)
      - Potential Risks
      - Simplified Explanation
      - Recommendations
   5. The analysis is returned as formatted markdown.

Q27: How does the AI doctor notes summary generation work?
A: When a doctor completes an appointment:
   1. Doctor enters free-text consultation notes.
   2. The notes are sent to an LLM with a structured prompt.
   3. LLM generates a summary with:
      - Symptoms (extracted)
      - Medication (prescribed)
      - Advice (given)
      - Diet Recommendation
   4. The summary is editable by the doctor before saving.
   5. Saved alongside the notes in appointment_notes table.

Q28: What AI models and services are used in MediQueue?
A: The AI services are:
   - OpenRouter (Primary LLM): Uses openai/gpt-oss-120b:free model
     for intent detection, FAQ answering, doctor search, symptom
     triage, appointment extraction, report analysis, and note
     summarization.
   - OpenAI Embeddings (via OpenRouter): text-embedding-3-small
     model for RAG knowledge base embeddings, routed through
     LangChain's OpenAI integration.
   - Google Gemini: Configured but not actively used in main flow.

Q29: How is the AI chatbot's intent detection implemented?
A: Intent detection uses a single LLM call with a structured prompt:
   - The system message defines the available intents: FAQ, DOCTOR,
     SYMPTOM, APPOINTMENT, QUEUE, HISTORY.
   - It provides descriptions and examples for each intent.
   - The user's message is sent to the LLM.
   - The LLM returns a JSON response with the detected intent.
   - Based on the intent, the appropriate handler is dispatched.

Q30: How does the conversational appointment booking work?
A: The appointment booking agent:
   1. Extracts structured data from natural language using LLM:
      - doctorName, date, time, symptoms
   2. Normalizes the date to YYYY-MM-DD format.
   3. Validates working hours (9 AM - 6 PM, excluding 1 PM lunch).
   4. Checks for appointment conflicts.
   5. Analyzes doctor workload.
   6. Creates the appointment in the database.
   7. Detects urgent symptoms and warns the user.
   8. Returns a confirmation message with appointment details.

7. FRONTEND & UI QUESTIONS
================================================================================

Q31: What UI library is used and why?
A: shadcn/ui is used because:
   - It provides accessible, customizable components built on Radix UI.
   - Components are copied into the project (not a dependency), giving
     full control over styling and behavior.
   - Works seamlessly with Tailwind CSS.
   - Includes components like Button, Card, Dialog, Input, Table,
     Sheet, Badge, and more.
   - Icons are provided by lucide-react.

Q32: How does the role-based sidebar navigation work?
A: The sidebar (app-sidebar.tsx) dynamically filters navigation items:
   - It receives the user's session (useSession()).
   - Navigation items are defined with allowedRoles arrays.
   - Items are filtered based on the user's role before rendering.
   - For example, "Doctors" link only shows for ADMIN, "Queue" shows
     for ADMIN and DOCTOR.
   - The sidebar also shows user info (name, role) in the footer.

Q33: How does the DataTable component work?
A: The DataTable (data-table.tsx) is a reusable component that:
   - Uses TanStack React Table v8 for table state management.
   - Accepts column definitions and data as props.
   - Provides built-in pagination with page size selector.
   - Includes search/filter functionality.
   - Shows skeleton loading states during data fetch.
   - Accepts custom action buttons per row (e.g., Edit, Delete).
   - Used across appointments, doctors, queue, and patient lists.

Q34: How does the chat widget work?
A: The chat widget (chat-widget.tsx + hospital-chat.tsx):
   - A floating button appears in the bottom-right corner.
   - Clicking opens a Sheet (slide-in panel) with the chat interface.
   - Shows message history with user/assistant bubbles.
   - Quick action buttons for common queries (Hospital Timings,
     Appointments, Diet Advice, Emergency).
   - Messages are sent to /api/chat endpoint.
   - Responses are streamed and displayed in real-time.

Q35: How does the appointment form handle patient lookup?
A: The appointment form includes a patient-lookup component:
   - Patient enters their phone number.
   - API calls /api/patients/search?phone= to find the patient.
   - If found, patient name and details auto-populate the form.
   - If not found, the system can create a walk-in patient record.
   - This reduces manual data entry and ensures patient records
     are linked to appointments.

Q36: How does the doctor notes modal work?
A: The doctor notes modal (doctor-notes-modal.tsx):
   - Opens when a doctor clicks "Complete" on a queue item.
   - Provides a text area for entering consultation notes.
   - "Generate Summary" button sends notes to /api/ai/summary.
   - AI summary is displayed in an editable text area.
   - Doctor can review and edit the AI-generated summary.
   - "Save & Complete" button saves notes and summary, then
     updates the appointment status to COMPLETED.

8. DEVOPS & DEPLOYMENT QUESTIONS
================================================================================

Q37: How is the application deployed?
A: The application is deployed on Vercel:
   - NEXTAUTH_URL environment variable points to the Vercel URL.
   - Database is hosted on Neon (serverless PostgreSQL).
   - Environment variables are configured in Vercel dashboard.
   - Automatic deployments on git push to main branch.
   - Serverless functions handle API routes.

Q38: What environment variables are required?
A: The required environment variables are:
   - DATABASE_URL: PostgreSQL connection string (Neon)
   - AUTH_SECRET: Secret for NextAuth JWT signing
   - OPENROUTER_API_KEY: API key for OpenRouter (LLM + embeddings)
   - GEMINI_API_KEY: Google Gemini API key (configured but optional)
   - NEXTAUTH_URL: Application URL for auth callbacks

Q39: How is testing set up in the project?
A: Testing uses Jest 30 with:
   - @testing-library/jest-dom for DOM matchers
   - ts-jest for TypeScript compilation
   - Jest configuration in jest.config.ts
   - Test files co-located with source files
   - Coverage reports for code quality tracking

Q40: How does the database connection work in a serverless environment?
A: The database connection (src/lib/db.ts):
   - Uses the 'pg' package to create a connection pool.
   - The pool is created once and reused across requests (important
     for serverless to avoid connection exhaustion).
   - Connection string comes from DATABASE_URL environment variable.
   - Neon provides serverless PostgreSQL with connection pooling
     built in, handling connection management at the infrastructure
     level.

9. SECURITY QUESTIONS
================================================================================

Q41: What security measures are implemented in MediQueue?
A: Security measures include:
   - Password hashing with bcryptjs (10 salt rounds)
   - JWT-based authentication with secure tokens
   - Role-based middleware protecting routes
   - Input validation using Zod schemas on all API endpoints
   - UUID primary keys preventing ID enumeration
   - Server-side rendering preventing client-side data exposure
   - Environment variables for sensitive configuration
   - CORS and CSRF protection via Next.js defaults

Q42: How is password security handled?
A: Password security:
   - Passwords are hashed using bcryptjs with 10 salt rounds.
   - Plain-text passwords are never stored in the database.
   - Login compares the hashed password using bcrypt.compare().
   - Password is excluded from JWT token and session data.
   - Registration validates password requirements via Zod schema.

Q43: How does the middleware prevent unauthorized access?
A: The middleware:
   - Runs on every request before the page loads.
   - Verifies the JWT token exists and is valid.
   - Checks the user's role against the allowed roles for the route.
   - Returns 401 if no token, redirects to /unauthorized if wrong role.
   - This prevents both unauthenticated and unauthorized access.

Q44: How is user input validated?
A: Input validation uses Zod schemas defined in src/lib/validations.ts:
   - registerSchema: Validates name, email, password, phone.
   - doctorSchema: Validates name, email, password, specialization.
   - appointmentSchema: Validates patient_id, doctor_id, date, time.
   - Each API route validates the request body against the
     appropriate schema before processing.
   - Invalid input returns 400 with descriptive error messages.

10. SCENARIO-BASED / PROBLEM-SOLVING QUESTIONS
================================================================================

Q45: How would you add a new feature like "Prescription Management"?
A: I would follow the existing architecture:
   1. Database: Add a prescriptions table (id, appointment_id FK,
      patient_id FK, doctor_id FK, medications JSONB, notes,
      created_at).
   2. Queries: Create src/lib/queries/prescriptions.ts with CRUD
      functions.
   3. API Routes: Create src/app/api/prescriptions/route.ts and
      [id]/route.ts.
   4. UI Components: Create prescription-form.tsx, prescriptions-table.tsx.
   5. Pages: Add /prescriptions page in the dashboard route group.
   6. Middleware: Add route protection (DOCTOR can create, PATIENT
      can view own prescriptions).
   7. Sidebar: Add navigation item with appropriate roles.

Q46: How would you handle a scenario where the AI chatbot gives an
     incorrect medical recommendation?
A: Safety measures:
   - The chatbot should always display a disclaimer: "This is not
     a substitute for professional medical advice."
   - Implement a confidence threshold - if the AI is uncertain,
     it should recommend consulting a doctor.
   - The symptom triage only recommends doctor specializations,
     not diagnoses or treatments.
   - The FAQ system constrains answers to the retrieved context,
     reducing hallucination.
   - Medical report analysis emphasizes "consult your doctor" in
     recommendations.

Q47: How would you optimize the system for high traffic?
A: Optimization strategies:
   - Database: Add indexes on frequently queried columns (status,
     appointment_date, doctor_id). Use connection pooling.
   - Caching: Cache doctor list and knowledge base responses in Redis.
   - AI: Cache LLM responses for repeated queries. Use streaming
     for real-time chat responses.
   - Frontend: Use React Server Components for initial data, client-side
     fetching for dynamic updates. Implement virtual scrolling for
     large lists.
   - Infrastructure: Use Vercel's edge functions and CDN for static
     assets.

Q48: How would you add real-time queue updates?
A: Real-time queue updates could use:
   - WebSockets via Socket.io or Pusher for live queue status.
   - Server-Sent Events (SSE) for simpler implementation.
   - Polling with React Query for automatic cache invalidation.
   - Implementation: Create a WebSocket server, subscribe queue
     page to updates, broadcast status changes from the queue
     update API endpoint.

Q49: How would you handle concurrent appointment bookings for the
     same slot?
A: The system handles this through:
   - Database-level: Unique constraints and transaction isolation.
   - Application-level: Conflict detection in the appointment
     creation flow checks for overlapping time slots.
   - Queue number assignment uses explicit transactions (BEGIN/
     COMMIT/ROLLBACK) to prevent race conditions.
   - Error handling returns a user-friendly message suggesting
     alternative time slots.

Q50: What would you improve in the current system?
A: Potential improvements:
   - Add email/SMS notifications for appointment confirmations
     and reminders.
   - Implement payment integration for consultation fees.
   - Add multi-language support for diverse patient populations.
   - Implement a proper audit log for compliance (HIPAA-like).
   - Add video consultation integration for telemedicine.
   - Implement a proper caching layer (Redis) for frequently
     accessed data.
   - Add comprehensive test coverage (unit, integration, e2e).
   - Implement rate limiting on AI endpoints to control costs.
